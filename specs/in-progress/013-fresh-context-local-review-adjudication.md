## Summary

- `/coding:local-review` stops adjudicating in the session that authored the change. Its default selector mode keeps the in-session CLASSIFY step and moves ADJUDICATE to exactly one fresh-context subagent.
- The subagent is a new read-only agent, `agents/selector-adjudicator.md`, whose whole input is the diff, the classified rule set, the mechanical findings and the repo path — it never sees the authoring conversation, so the rationale that produced the code cannot talk it out of a finding.
- The clean path stays free: when nothing is applicable and the mechanical funnel is empty, the existing short-circuit still fires and no subagent is dispatched.
- A dispatch that fails or returns nothing is a Must Fix toolchain failure, never a silent clean report.
- `/coding:pr-review` and `/coding:code-review` keep in-session adjudication — their zero-spawn path is unchanged.

## Problem

Selector mode was built to decouple review wall-time from rule count, and it does that by running CLASSIFY and ADJUDICATE inside the calling session. That design goal — stated in `docs/selector-mode-guide.md` as "the design goal is zero sub-agent spawns" — quietly assumed the calling session is neutral. Under `/coding:local-review` it is not: the calling session is the session that just wrote the code.

The result is a selection function and an evaluation function that share a context window, a system prompt, an invocation and a tool set. The Five-Lens gate analysis (shortlist item 3) named this exactly: "each lens is a fresh subagent that never saw the authoring conversation; a single pass in own context is not a substitute". An in-session adjudicator that has just written a global variable and explained to itself why the global variable is fine will read the `go-architecture/no-globals-or-singletons` rule block and find a reason not to fire it. The finding is not dropped maliciously; it is dropped because the justification is already in context and reads as settled.

`/coding:pr-review` carries the same in-session wording, but its bot path already runs in its own container, so the contamination there is bounded and out of scope for this change.

## Goal

Under `/coding:local-review` in selector mode, the ADJUDICATE step runs as exactly one subagent that receives the diff, the classified rule set, the mechanical findings and the repo path, and nothing else. Its verdict is the review's verdict. On a diff where the authoring session's own stated rationale would excuse a real violation, the fresh-context run reports the finding while the pre-change in-session run did not.

The cost is bounded at one extra dispatch per review that has something to adjudicate — never on the clean path. Recall does not fall: the bench re-run after the change scores at or above the recorded baseline.

## Non-goals

- Do NOT change `full` mode, `short` mode, or the per-owner dispatch path.
- Do NOT change `/coding:pr-review` or `/coding:code-review` — both keep in-session adjudication and their zero-spawn property.
- Do NOT move CLASSIFY into the subagent. It stays in-session: the task's first success criterion names the classified rule set as an input the subagent receives, and keeping it in-session preserves the zero-spawn clean path. The residual contamination at the skip decision is a stated limit, recorded in the guide, not a hidden one.
- Do NOT add a fix loop, a re-review round, or an unbounded re-dispatch on a failed adjudication.
- Do NOT add a config knob, a flag, or a mode token — the fresh-context dispatch is the behaviour of the existing default mode.
- Do NOT change `scripts/rule-checks.sh`, `scripts/ast-grep-runner.sh`, `scripts/validate-citations.sh`, `rules/index.json` or `.maintainer.yaml`.
- Do NOT touch the security pipeline or the `--security` flag.

## Assumptions

- **The calling session is the authoring session under `/coding:local-review`.** That is what makes the contamination real; it is not asserted from the code, and AC9 is the run that tests it.
- **A fresh context reaches a different verdict than the authoring context** on a diff whose rationale is in the authoring conversation. This is the hypothesis the whole change rests on, and AC9 is its test — if the fresh run excuses the violation too, the change buys nothing and the Failure Modes row for a recall-neutral-but-inert dispatch applies.
- **The fresh-context dispatch does not lose recall.** A subagent reading the same rule blocks over the same diff should reach at least the in-session verdict; AC11 tests it against the recorded baseline rather than assuming it.
- **The bench baseline is reproducible** at the same pin, model, effort and mode. AC11 requires both figures from complete runs over the same `prs_version`; if the baseline cannot be reproduced, the comparison is unsound and must be re-established first.

## Desired Behavior

1. **A read-only fresh-context adjudicator agent exists.** `agents/selector-adjudicator.md` follows `docs/agent-command-development-guide.md` and declares `tools: Read, Grep, Glob` — no `Write`, no `Edit`, no `Bash`. It states its role as the ADJUDICATE half of selector mode, run in a context that never saw the authoring conversation, and it states plainly that it must not infer, request or reconstruct the author's rationale. It reads only the `### RULE <id>` blocks of the rules it is given, resolving each `doc_path` against the coding plugin's own `docs/` dir with the same two-step plugin-root resolution the selector guide already uses — never a filesystem search.

2. **The adjudicator receives four named inputs and nothing else.** The caller passes `DIFF` (the diff, written by the caller to a session-local path outside the reviewed tree, mirroring the `/tmp/pr-review-findings.json` convention), `CLASSIFIED_RULES` (the Step 4c-sel applicable rule-id list), `MECHANICAL_FINDINGS` (the Step 4a runner output path) and `REPO_PATH` (the reviewed directory, absolute). The prompt carries no conversation history, no authoring rationale and no session state. The four are named in the command, so a reader checking what the fresh context sees does not have to infer it.

3. **`/coding:local-review` Step 4d-sel is one dispatch.** In selector mode the command spawns exactly one `coding:selector-adjudicator` Task via the Task tool, with the four inputs above, and uses its returned findings as the adjudication result. The subagent performs its own batching when the applicable set exceeds 20 rules — the caller still spawns once. The caller keeps citation validation: it writes the returned findings to a session-local JSON, runs `scripts/validate-citations.sh` over them from the plugin root, and consolidates the survivors into the Step 5 report.

4. **The clean path dispatches nothing.** Step 4c-sel still runs in-session and still short-circuits on an empty applicable set with empty mechanical findings, printing `selector clean — no adjudication needed` and proceeding to Step 5 without any dispatch. The dispatch happens only when there is something to adjudicate.

5. **The guide carries the variant without disturbing the base.** `docs/selector-mode-guide.md` documents the fresh-context dispatch as the `/coding:local-review` form of Step 4d-sel, alongside the in-session form `/coding:pr-review` and `/coding:code-review` keep. The `## Inputs` table gains the four fresh-context input names, scoped to the caller that sets them. The recall-contract sentence, the Step 4c-sel CLASSIFY procedure and its HARD INVARIANT, the security extension and the traceability section are unchanged. The guide's opening line — the one stating the zero-sub-agent-spawn design goal, which the Problem section quotes as the flawed assumption — is qualified so it no longer reads as the shipped behaviour of `/coding:local-review`; `scripts/acceptance.sh` does not assert that line, so rewording it is safe.

6. **A failed dispatch is not-clean.** If the `coding:selector-adjudicator` dispatch fails, errors or returns nothing, the caller reports it as a **Must Fix toolchain failure** naming the dispatch, and the judgment tier reads as not-run. It never degrades to a mechanical-findings-only report presented as a complete selector review, and it is retried at most once. This is the same fail-fast discipline Step 4.0 and Step 4b already apply to a missing `ast-grep` or a missing selector guide.

7. **The behaviour is regression-locked twice.** `scripts/acceptance.sh` gains a selector-dispatch block asserting the agent file exists, the command names `coding:selector-adjudicator`, and the four input labels are present — with the agent name as a literal, never derived from the run's own output, so the assertion fails when the wiring is removed. ## Constraints

- **Scope of the change is `/coding:local-review` only.** `commands/pr-review.md` is not edited. The shared guide is edited additively, so the two in-session callers keep their byte-for-byte procedure.
- **CLASSIFY stays in-session (frozen).** The skip decision keeps the authoring session's context, and that is a stated limit rather than an oversight: the task's first success criterion names the classified rule set as a subagent input, and moving CLASSIFY would spawn on every run including the clean one. The guide says so in words, so the residual contamination is visible to a reader rather than discovered by one.
- **Read-only adjudicator.** `tools: Read, Grep, Glob`. The agent never writes to the reviewed tree, never writes findings to disk, and never runs a build or scan command. The caller owns the findings file and the citation validation.
- **Four inputs, no fifth channel.** The dispatch prompt carries the four named inputs and nothing else — no summary of the authoring conversation, no "the author intended X", no prior report. A caller that finds itself wanting to explain the diff to the adjudicator has found the contamination this change exists to remove.
- **Fail-closed, single retry.** A dispatch failure is a Must Fix toolchain failure. One retry is permitted; a second failure is reported, never swallowed.
- **Acceptance literals are frozen.** `scripts/acceptance.sh` asserts the verbatim string `selector clean — no adjudication needed`, the `GUIDE_OK`/`GUIDE_MISSING` block, the step labels `4c-sel` and `4d-sel`, the heading tokens `CLASSIFY` and `ADJUDICATE`, the routing phrases `Selector mode (default)` and `Selector mode (the default)`, and the sentence `When uncertain, include.` All of them survive this change.
- **No new ast-grep YAML and no rule-base change.** `rules/index.json` is untouched, so `check-index` and `check-coverage` see no drift.
- **Marker hygiene on added lines.** The `self-containment/*` rule family shipped in v0.59.0 scans changed files whole, and it exempts exactly six paths — `specs/`, `prompts/`, `docs/self-containment-guide.md`, `agents/self-containment-assistant.md`, `scripts/rule-checks.sh` and `scripts/testdata/`. This change adds lines to `commands/`, `docs/selector-mode-guide.md`, `scenarios/011-fresh-context-adjudication-dispatch.md`, `README.md`, `llms.txt` and `CHANGELOG.md` — **none of them exempt**, `scenarios/` included — so every added line carries no home-directory path, no requirement id, no planning-directory reference and no revision or sign-off meta. Only the spec and prompt files under `specs/` and `prompts/` are exempt and may name them.
- **Generic content only.** Every example uses User, Order, Product, Customer — never a trading or project-specific domain. The agent and the guide use no operator-specific path.
- **Release tail.** `.dark-factory.yaml` sets `autoRelease: false`; the release is cut by the maintainer-agent-releaser per `.maintainer.yaml` (`autoRelease: true`). This spec requires only the CHANGELOG `## Unreleased` entry.

## Security / Abuse Cases

- **Attacker-controlled input:** the diff and the mechanical findings are the only content the fresh-context adjudicator reads, and both are already untrusted in the existing funnel. The change strictly *narrows* what the adjudicator can be influenced by: the in-session path let the authoring conversation act as an unlabelled input, and the fresh-context path removes it.
- **No new trust boundary:** the adjudicator reads files under the reviewed tree and the plugin's own `docs/`. It gains no network path, no credential and no write.
- **Read-only posture:** the tool line is the enforcement — a review that could write to the tree it reviews would be a new failure mode, and AC1 fails if the line ever admits `Write`, `Edit` or `Bash`.
- **Fail-closed on silence:** the highest-risk outcome for a review gate is a clean-looking report produced by a tier that did not run. The dispatch failure path is Must Fix for exactly that reason, and AC5 asserts it.
- **What can hang, retry forever, or race:** the dispatch is a single Task call with a single permitted retry; there is no loop, no background work and no shared mutable state. The findings file is session-local and written by one caller.
- **Provenance integrity:** every emitted finding cites a `rule_id` present in `rules/index.json`; the caller validates before consolidation, so an invented id cannot survive into the report.

## Do-Nothing Option

If this does not ship, `/coding:local-review` keeps adjudicating inside the session that wrote the code, and the local pre-PR loop keeps certifying changes with a reviewer that shares the author's blind spots.
