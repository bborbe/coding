## Summary

- Ship the security review **pipeline** layer of Security Review Mode on top of the shipped 5-rule mechanical rule base (task 1, v0.46.0): the recon pass derives a per-review `security-model.json` — entry points, identities, auth mechanisms, resources with `authorization_functions`, trust boundaries, invariants — each entry evidence-pointered with `file:line`, and the model is **never committed** to any repo.
- Freshness gate keeps cost bounded: entries whose evidence source changed in the diff are re-derived; unchanged entries carry forward; stale-model events surface in the report with the literal `model refresh:` line.
- Classifier gains six security trait groups (`authz`, `input-origin`, `data-to-sink`, `external-io`, `crypto`, `secrets`) with **non-negotiable over-selection for `authz`** on resource-handler diffs; invariants are selected **deterministically** when the diff touches any entry point in their `attack_surfaces`.
- Adjudicator prompt input gains the diff-relevant model subset plus the applicable invariants with their evidence authorization functions; the attack-surface inventory emits as a drift signal that is the diff→traits bridge for security.
- All behavior ships as a documented, reproducible procedure in the plugin's docs layer: a new `docs/security/security-review-pipeline.md` (derivation contract) plus an extension to `docs/selector-mode-guide.md` (classify/adjudicate consumption). No command is wired yet (task 4), no new search infrastructure, no new RULE blocks, no Go code.

## Problem

The shipped rule base is a linter: mechanical detectors fire on AST shapes and citation validation proves the findings came from the rule set, but the security findings that actually matter — IDOR and authorization bugs — cannot be found by a shape. They require knowing the reviewed app's entry points, its identities and auth mechanisms, its resources and the authorization functions that gate them, and its cross-cutting security invariants. That state is project-specific, per-repo, and currently absent from the review session. Without a derived model the judgment and invariant tiers promised as the follow-up to task 1 have nothing to adjudicate against, and the security rules stay mechanical-only — the design's differentiator (the invariant/authz layer generic linters miss) never ships. This spec builds that layer.

## Goal

After this work, a review session that runs Security Review Mode can, in-session and before adjudication, derive an evidence-pointered security model of the repo under review (entry points, identities, auth mechanisms, resources + authorization functions, trust boundaries, invariants), keep that model fresh and bounded via the freshness gate and diff-relevant truncation, and feed a security-aware classifier and adjudicator that over-select `authz` on resource-handler diffs and deterministically select invariants on `attack_surfaces` hits — all as a documented, reproducible procedure in the plugin, with the model existing only for the current review session and never committed anywhere.

## Desired Behavior

1. **Recon pass procedure.** A new `docs/security/security-review-pipeline.md` documents, as a step-by-step in-session procedure, how the review session derives the security model before classification: enumerate entry points (routes/handlers) from the diff's touched packages plus the index of existing handlers when available; resolve identities (anonymous, authenticated, member, admin, service-account) and auth mechanisms (session-cookie, api-token) from the codebase; resolve resources and their `authorization_functions` via symbol resolution against the codebase, reusing the existing `trigger` glob machinery, the `@commits` special-case, and the ast-grep funnel — no new search infrastructure; derive invariants as `resource → identifier → authorization_function` with the function's `file:line` as evidence. The procedure is recall-oriented for entry points: a missed entry point is a permanent blind spot, and over-listing is cheap. The guide is a procedure contract, not an enforceable rule guide: it contains zero `### RULE` headings.
2. **Model schema and lifecycle.** The guide specifies the `security-model.json` schema: `version`, `derived_from` (repo, head, review_id), `entry_points[]` (type, method, path, handler, auth, evidence), `identities[]`, `auth_mechanisms[]`, `resources[]` (name, identifiers, `authorization_functions[]`, evidence), `trust_boundaries[]`, `external_interactions[]`, `invariants[]` (id, statement, evidence, `attack_surfaces[]`). Every entry carries `file:line` evidence. The model is derived in-session at review start, exists only for the current review session, is written to a session-local path outside the reviewed repo's tree (mirroring the existing `/tmp/pr-review-findings.json` pattern), and is **never committed** to any repo.
3. **Freshness gate and size control.** The guide specifies that at review start each candidate entry's evidence source is compared against the diff: an entry whose source changed in the diff is re-derived; an unchanged entry carries forward; stale-model events surface in the report with the literal `model refresh:` line naming the affected entry. Classifier and adjudicator input are truncated to diff-relevant entries — the entry points and invariants whose attack surface the diff touches — plus the cheap inventory counts, keeping model context cost bounded on large repos.
4. **Attack-surface inventory as drift signal.** The guide specifies the countable per-review attack-surface inventory (HTTP endpoints, authenticated, admin-only, file uploads, external URL inputs, webhooks, HTML rendering, database queries) with the deterministic diff→traits bridge: a count change in a category selects the matching security trait group (new HTTP endpoint → `authz` + `input-origin`; new file upload → `input-origin` + `data-to-sink`; new external-URL input → `external-io` + `input-origin`; new webhook → `external-io` + `authz`; new render path → `input-origin`; new DB query → `data-to-sink`). The inventory is a drift signal that makes the model checkable and the diff→traits selection deterministic.
5. **Classifier extension — security trait groups.** `docs/selector-mode-guide.md` gains a security-gated classifier sub-step (active only when the session carries the security-review signal, which task 4's command wiring sets): security-relevant selection is grouped into exactly six trait groups — `authz`, `input-origin`, `data-to-sink`, `external-io`, `crypto`, `secrets`. **Over-selection for `authz` is non-negotiable**: any diff touching a resource handler (a diff that changes a file cited as evidence by an entry point operating on a modeled resource, or a file cited as evidence by a modeled resource's `authorization_function`) MUST select the `authz` group — a missed authz rule is worse than an extra evaluation. `crypto` and `secrets` are selected when the corresponding mechanical findings (`go-security/crypto-*`, `go-security/hardcoded-secret`) are present in the Step 4a output or the diff changes a file that imports `crypto/*`/`hash/*` or calls a crypto/secret-handling function (the specific trigger is: a changed file whose import list or function calls include the symbols those mechanical rules flag — agent decides at impl time which exact rule id applies). The applicable set remains a subset of the Step 4b-i candidate set.
6. **Deterministic invariant selection.** The classifier sub-step specifies that invariants are selected deterministically, with no LLM judgment: if the diff changes the evidence file of any entry point whose path appears in an invariant's `attack_surfaces`, or the diff changes the invariant's own evidence source, that `invariant_id` is in the applicable set. Invariants behave like the architecture tier — always considered when their attack surface is touched, never subject to a skip decision.
7. **Adjudicator input extension.** `docs/selector-mode-guide.md` specifies that the adjudicate step's input gains: the diff-relevant security model subset, the applicable invariants with their evidence authorization functions, and the attack-surface inventory as a drift signal. Each applicable invariant is judged against the diff slice with the single question: does this change preserve the invariant? Invariant-kind findings cite `invariant_id` (the polymorphic finding contract); validation of those IDs is task 3. The report contract (documented now, wired in task 4) includes a Security Model section with `derived_from`, entry-point count, inventory counts, and any `model refresh:` lines.
8. **Integration and scope-lock.** README.md gains a table row for `docs/security/security-review-pipeline.md`; llms.txt gains a matching bullet. No new agent, no CLAUDE.md Doc↔Agent row (the guide is a procedure contract, not an enforceable rule guide). `commands/*.md`, `scripts/validate-citations.sh`, and `agents/*.md` are untouched; `docs/security/security-review-guide.md` stays at exactly 5 RULE blocks; `rules/security/*.yml` stays at exactly 5 detectors; `rules/index.json` stays at 171 entries. A `## Unreleased` CHANGELOG section with a bullet describing the security review pipeline is added.

## Security / Abuse Cases

The feature reads untrusted repo diffs and derives a session-local model; it introduces no network calls, no credentials, and no writes outside a session temp path.

- **Attacker-controlled input:** the recon reads the diff and changed code of the repo under review — untrusted content. The model is LLM-derived text consumed only by the LLM adjudicator; it is never executed, never parsed as code, and never fed into a shell or build step, so there is no code-injection path beyond what the existing LLM adjudication already accepts.
- **Trust boundary:** nothing crosses outward. No network probing (phase 2), no external calls, no credential access. The reviewed repo cannot absorb the model because the model is written to a session-local path outside the repo tree and never committed — a malicious repo gains no new artifact.
- **Evidence fields:** `file:line` strings are display-only references recorded from the diff/package; the recon writes no files to those paths, so path traversal into the reviewed tree is not a reachable surface.
- **Resource exhaustion:** model context is bounded by diff-relevant truncation plus the countable inventory; a hostile mega-repo cannot force unbounded model growth into the classifier/adjudicator input.
- **Review-timing abuse:** a repo could over-list entry points to inflate review work; over-listing is cheap by the recall contract, and the inventory counts keep the surface countable and reportable.
- **Provenance:** invariant-kind findings cite `invariant_id` per the polymorphic finding contract; validation (and rejection of invented invariants) is task 3's citation-validator extension — out of scope here, so this spec ships no new validation gate.
- **Hang/retry:** the recon is a bounded in-session procedure over the already-fetched diff and worktree; there is no retry loop and no unbounded scan.
