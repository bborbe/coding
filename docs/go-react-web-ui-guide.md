# Go Web UI Stack: React, TypeScript, Vite, and go:embed

The one stack for a Go service that needs a web UI: a **Go JSON API**, a **React + TypeScript + Vite** frontend built into `frontend/dist`, embedded in the binary with `go:embed`, and **Server-Sent Events** for live updates.

Use it when a service needs a UI of its own — a dashboard, an editor, a control page. Do not use it for a static content site; those stay on Astro (see the Development Guide's exception).

The shape is deliberately narrow, and every part earns its place:

- **One binary.** The frontend is built and embedded, so the binary and the assets always ship together — no runtime path, mount or flag.
- **One contract.** Every UI action goes through the JSON API, so an agent, a CLI or an MCP tool can use the same API the page uses.
- **One type source.** TypeScript types are generated from the Go structs, so the two have nothing to drift *apart* — provided the generator runs and nobody hand-edits its output.
- **One transport seam.** A single module talks to the backend; everything else reads the model it returns.

The examples below use a generic `Order` resource. The same shapes apply to any resource — swap the name and the fields.

## Repository layout

A service using this stack has a Go package at the root and a `frontend/` directory beside it. The frontend is built into `frontend/dist`, which `go:embed` carries into the binary.

```
service/
├── go.mod                  # module example.com/service
├── go.sum
├── .gitignore              # ignores frontend/dist/* except .gitkeep
├── assets.go               # go:embed of frontend/dist
├── main.go                 # flags, router, source wiring
├── Makefile                # frontend, types, test, check, e2e targets
├── tools.env               # TYGO_VERSION and other tool pins
├── tygo.yaml               # Go structs → TypeScript types
├── pkg/handler/
│   ├── orders.go           # Order struct, OrderSource, JSON handler
│   ├── events.go           # SSE handler
│   └── page.go             # serves the embedded frontend
└── frontend/
    ├── index.html          # Vite entry, <div id="root">
    ├── package.json        # React, Vite, TypeScript, Vitest, Playwright
    ├── package-lock.json   # commit it — npm ci needs it
    ├── tsconfig.json       # strict
    ├── vite.config.ts      # dev proxy + Vitest config
    ├── playwright.config.ts
    ├── e2e/                # Playwright specs
    └── src/
        ├── main.tsx        # React root
        ├── App.tsx
        ├── App.test.tsx    # Vitest component test
        ├── api.ts          # the only module that talks to the backend
        ├── types.ts        # generated by tygo — do not edit
        ├── setupTests.ts   # jest-dom matchers for Vitest
        └── styles.css      # the house palette
```

Two details matter more than they look. First, `frontend/dist` is **git-ignored except for a `.gitkeep`**: the directory must exist for `go:embed` to compile, but the built output is never committed. Second, the frontend is built by a make target, never by hand — the embedded build and the served assets must be the same bytes.

The entry mounts `App` into the `#root` element `index.html` provides, and imports the palette once:

```tsx
// src/main.tsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App";
import "./styles.css";

createRoot(document.getElementById("root") as HTMLElement).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
```

## The API contract in Go

The Go structs are the contract: the JSON the handler writes and the TypeScript types tygo generates both derive from them. Keep them in one package so tygo can read them.

```go
// pkg/handler/orders.go
package handler

import (
	"context"
	"encoding/json"
	"net/http"
	"time"
)

// Order is the resource the page reads. Its json tags are the wire contract.
type Order struct {
	ID       string    `json:"id"`
	Customer string    `json:"customer"`
	Total    float64   `json:"total"`
	Status   string    `json:"status"`
	Created  time.Time `json:"created"`
}

// OrderSource supplies the orders. The mock reads a fixture; the live source
// reads the database. Swapping them changes nothing else in the service.
type OrderSource interface {
	Orders(ctx context.Context) ([]Order, error)
}

// NewOrdersHandler serves the orders as JSON at GET /api/orders.
func NewOrdersHandler(source OrderSource) http.Handler {
	return http.HandlerFunc(func(resp http.ResponseWriter, req *http.Request) {
		orders, err := source.Orders(req.Context())
		if err != nil {
			http.Error(resp, "read orders failed", http.StatusInternalServerError)
			return
		}
		if orders == nil {
			orders = []Order{} // a JSON array endpoint returns [], never null
		}
		body, err := json.Marshal(orders)
		if err != nil {
			http.Error(resp, "marshal orders failed", http.StatusInternalServerError)
			return
		}
		resp.Header().Set("Content-Type", "application/json")
		_, _ = resp.Write(body)
	})
}

// NewMockOrderSource returns a fixture-backed source. Swap it for the live
// source when the data is ready; the page and the JSON shape never change.
func NewMockOrderSource() OrderSource {
	return mockOrders{}
}

type mockOrders struct{}

func (mockOrders) Orders(context.Context) ([]Order, error) {
	return []Order{{ID: "o-1", Customer: "Ada", Total: 41, Status: "paid"}}, nil
}
```

The `OrderSource` interface is the seam that lets the same handler serve mock data first and a live source later: the page and the JSON shape never change.

## The Go side: embed and serve

Bootstrap the module once with `go mod init example.com/service` and `go get github.com/gorilla/mux`, then the embedding is three lines. `make build` runs the Vite build first, so the served assets and the binary always ship together.

```go
// assets.go
package main

import "embed"

//go:embed all:frontend/dist
var frontendDist embed.FS
```

`main.go` parses a `-listen` flag, wires the source, and mounts three things: a health check, the JSON API, and the page handler. `go:embed` carries the built `dist/`, and `fs.Sub` opens that sub-tree:

```go
// main.go
package main

import (
	"flag"
	"io/fs"
	"log"
	"net/http"
	"time"

	"github.com/gorilla/mux"

	"example.com/service/pkg/handler"
)

func main() {
	// loopback by default: a bare ":9090" binds every interface, which
	// contradicts the unauthenticated-JSON warning further down.
	listen := flag.String("listen", "127.0.0.1:9090", "HTTP listen address")
	flag.Parse()

	source := handler.NewMockOrderSource() // swap for the live source; the page never changes

	dist, err := fs.Sub(frontendDist, "frontend/dist")
	if err != nil {
		log.Fatal(err) // the embed directive guarantees this tree exists
	}

	router := mux.NewRouter()
	router.Path("/healthz").HandlerFunc(func(w http.ResponseWriter, _ *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	router.Path("/api/orders").Methods(http.MethodGet).Handler(handler.NewOrdersHandler(source))
	router.Path("/api/orders/events").Methods(http.MethodGet).Handler(handler.NewOrderEventsHandler(source, 2*time.Second))
	router.PathPrefix("/").Handler(handler.NewPageHandler(dist))

	log.Fatal(http.ListenAndServe(*listen, router))
}
```

The page handler lives in `package handler` beside the others, so `main` only wires it:

```go
// pkg/handler/page.go
package handler

import (
	"io/fs"
	"net/http"
	"strings"
)

// NewPageHandler serves the embedded frontend. Unknown paths fall back to
// index.html so a client-side route still loads; a missing build reports 503
// rather than serving an empty document.
func NewPageHandler(dist fs.FS) http.Handler {
	fileServer := http.FileServer(http.FS(dist))
	return http.HandlerFunc(func(resp http.ResponseWriter, req *http.Request) {
		path := strings.TrimPrefix(req.URL.Path, "/")
		if path != "" {
			if _, err := fs.Stat(dist, path); err == nil {
				fileServer.ServeHTTP(resp, req)
				return
			}
		}
		index, err := fs.ReadFile(dist, "index.html")
		if err != nil {
			http.Error(resp, "frontend not built", http.StatusServiceUnavailable)
			return
		}
		resp.Header().Set("Content-Type", "text/html; charset=utf-8")
		_, _ = resp.Write(index)
	})
}
```

Run the whole package, not `main.go`: `frontendDist` lives in `assets.go`, so `go run main.go` compiles that one file alone and fails with `undefined: frontendDist`. Use `go run .`.

## TypeScript configuration

`strict` is on, and the build runs `tsc --noEmit` before Vite, so a type error fails the build rather than shipping.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,
    "types": ["vitest/globals"]
  },
  "include": ["src", "vite.config.ts", "playwright.config.ts"]
}
```

`include` names the two config files as well as `src`: `tsc --noEmit` type-checks only what it includes, so a bare `"include": ["src"]` leaves `vite.config.ts` and `playwright.config.ts` unchecked — exactly the files where a wrong option type is silent until runtime.

`noUnusedLocals` and `noUnusedParameters` catch the dead prop or unused import a review would otherwise flag. `types` pulls in the Vitest globals so tests type-check. The jest-dom matchers are **not** listed in `types` — the wrong augmentation (`@testing-library/jest-dom` augments a global jest namespace, and with Vitest 5 it clashes on the `Assertion` type). Instead `src/setupTests.ts` imports `@testing-library/jest-dom/vitest`, which augments Vitest's own `Assertion` once, and that file is inside `include`:

```ts
// src/setupTests.ts
import "@testing-library/jest-dom/vitest";
```

## Vite configuration and the dev proxy

During development the page runs on the Vite dev server and proxies `/api` to the Go service, so the frontend reads the same `/api/orders` the embedded build does. In production there is no proxy — the Go server serves both the page and the API on one origin.

```ts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  build: { outDir: "dist", emptyOutDir: true },
  server: {
    proxy: { "/api": "http://127.0.0.1:9090" },
  },
  test: {
    environment: "jsdom",
    globals: true,
    setupFiles: ["./src/setupTests.ts"],
    // e2e/ holds Playwright specs; its test() API cannot run under Vitest.
    exclude: ["node_modules/**", "dist/**", "e2e/**"],
  },
});
```

The `exclude` line is load-bearing: Playwright and Vitest both export `test`, and without it Vitest tries to run the Playwright specs and fails. `jsdom` (a dev dependency) provides the DOM Vitest renders into.

## Generating TypeScript types from Go

`tygo` generates `frontend/src/types.ts` from the Go structs in `pkg/handler`, so there is one declaration of the shape rather than two. That holds only while the generator runs: edit the Go structs, run `make types`, and never hand-edit `types.ts` — a hand edit is the one way the generated file can disagree with the struct, and the next `make types` silently erases it.

```yaml
# tygo.yaml
packages:
  - path: "example.com/service/pkg/handler"
    output_path: "frontend/src/types.ts"
    type_mappings:
      time.Time: "string"   # time.Time serialises to an RFC3339 string
    frontmatter: |
      // Code generated by tygo from pkg/handler. DO NOT EDIT.
```

```makefile
.PHONY: types
types:
	go run github.com/gzuidhof/tygo@$(TYGO_VERSION) generate
```

Every tool the Makefile invokes with `go run …@$(VERSION)` is pinned in `tools.env`, which the Makefile includes — so the build is reproducible and a version bump is one line:

```makefile
# tools.env — one pin per tool the Makefile runs via `go run …@$(VERSION)`
TYGO_VERSION             ?= v0.2.21
GOLANGCI_LINT_VERSION    ?= v2.15.0
GOVULNCHECK_VERSION      ?= v1.3.0
```

The `type_mappings` entry is what turns `time.Time` into `string` rather than `any`; without it the generated `Created` field is untyped and the page can do nothing with it.

An OpenAPI spec is the usual alternative and was rejected here: it adds a second artifact to keep current for a single-consumer internal API. tygo reads the structs directly, so there is nothing to keep in sync.

## The single transport seam

One module talks to the backend; every component reads the model it returns. That is what keeps a mock-to-live swap a backend-only change: the page never knows whether the data is mock or live.

```ts
// api.ts — the only module that talks to the backend.
import type { Order } from "./types";

export const ORDERS_URL = "/api/orders";
export const ORDER_EVENTS_URL = "/api/orders/events";

export async function fetchOrders(signal?: AbortSignal): Promise<Order[]> {
  const response = await fetch(ORDERS_URL, { signal });
  if (!response.ok) {
    throw new Error(`GET ${ORDERS_URL} failed: ${response.status}`);
  }
  return (await response.json()) as Order[];
}
```

Keep every `fetch` here. A component that calls `fetch` directly is the seam leaking, and the next transport change has to hunt it down.

## Live updates with Server-Sent Events

Use SSE, not WebSocket, unless the browser must stream data **back** to the server. SSE is one-way server→client, rides plain HTTP, reconnects on its own, and needs no extra protocol — which is what a dashboard wants. A WebSocket is justified only when the page sends a continuous stream up (a terminal, a collaborative editor).

These examples bind loopback (`-listen`) and serve unauthenticated JSON. A service exposed beyond loopback must put the API behind the same auth as its admin server, and the SSE endpoint must validate `Origin` — an `EventSource` sends cookies, so an unvalidated stream is a cross-origin read.

The handler asserts `http.Flusher`, sets the event-stream headers, and emits **only when the payload changes**, so a client refreshes only on real changes. It lives in its own file, `events.go`, in the same package as `orders.go` — Go imports are file-scoped, so it carries its own import block:

```go
// pkg/handler/events.go
package handler

import (
	"encoding/json"
	"fmt"
	"net/http"
	"time"
)

func NewOrderEventsHandler(source OrderSource, interval time.Duration) http.Handler {
	return http.HandlerFunc(func(resp http.ResponseWriter, req *http.Request) {
		flusher, ok := resp.(http.Flusher)
		if !ok {
			http.Error(resp, "streaming unsupported", http.StatusInternalServerError)
			return
		}
		resp.Header().Set("Content-Type", "text/event-stream")
		resp.Header().Set("Cache-Control", "no-cache")
		// Deliberately no WriteHeader here: the status must stay unwritten until
		// the first successful emit, so a source error can still become a 500
		// instead of an empty 200 the client cannot tell from "no data".

		var last string
		emit := func() bool { // returns false when the stream must stop
			orders, err := source.Orders(req.Context())
			if err != nil {
				return false
			}
			payload, err := json.Marshal(orders)
			if err != nil {
				return false
			}
			if string(payload) == last { // unchanged: send nothing
				return true
			}
			last = string(payload)
			if _, err := fmt.Fprintf(resp, "event: orders\ndata: %s\n\n", payload); err != nil {
				return false
			}
			flusher.Flush()
			return true
		}

		if !emit() { // nothing written yet, so this can still be an error status
			http.Error(resp, "order source unavailable", http.StatusInternalServerError)
			return
		}
		ticker := time.NewTicker(interval)
		defer ticker.Stop()
		for {
			select {
			case <-req.Context().Done():
				return
			case <-ticker.C:
				if !emit() {
					return
				}
			}
		}
	})
}
```

One cost is worth stating rather than hiding: each connected client runs its own ticker and calls `source.Orders`, so N viewers mean N polls per interval. For a handful of dashboards that is nothing. Past that — or when `Orders` is an expensive query — share one ticker and fan the payload out to the connected clients, so the source is polled once per interval however many viewers are attached.

The client subscribes with `EventSource` and re-reads the JSON endpoint on each event, so one code path builds the model:

```ts
export function subscribeOrders(onChange: () => void): () => void {
  // jsdom (Vitest) has no EventSource; tests drive updates through fetch mocks.
  if (typeof EventSource === "undefined") {
    return () => undefined;
  }
  const source = new EventSource(ORDER_EVENTS_URL);
  source.addEventListener("orders", onChange);
  return () => source.close();
}
```

The component wires both together — load once, then reload on each event:

```tsx
useEffect(() => {
  const controller = new AbortController();
  const load = () =>
    fetchOrders(controller.signal).then(setOrders).catch((err: Error) => {
      if (err.name !== "AbortError") setError(err.message);
    });
  load();
  const unsubscribe = subscribeOrders(load);
  return () => {
    unsubscribe();
    controller.abort();
  };
}, []);
```

The `typeof EventSource === "undefined"` guard is not defensive noise: jsdom has no `EventSource`, so without it every Vitest render of a component that subscribes throws.

## The house palette

Use **plain CSS variables** — the house dark palette — declared once at the root. Do not invent a palette, and do not adopt a component library's tokens unless you map them onto these variables first. `color-scheme: dark` is load-bearing, not decoration: it makes the browser render scrollbars, form controls and the canvas backdrop dark too.

```css
:root {
  color-scheme: dark;
  --bg: #111418;
  --panel: #1a1f26;
  --border: #2a3038;
  --text: #e8edf2;
  --muted: #8b95a3;
  --accent: #4f8cff;
  --ok: #38c172;
  --warn: #d08b5b;
  --err: #e55b5b;
}

body {
  margin: 0 auto;
  max-width: 860px;
  padding: 24px;
  background: var(--bg);
  color: var(--text);
  font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
}

.subtitle { color: var(--muted); font-size: 13px; }
.err { color: var(--err); }
```

The status colours carry meaning, so do not use them decoratively: `--ok` / `--warn` / `--err` describe an outcome — success, caution, failure — never a heading's mood. This is the house palette; a React app uses it verbatim — do not invent colours or adopt a library's tokens unmapped.

## Testing with Vitest and Playwright

Two layers, each with a job. **Vitest** (jsdom) tests the component against a mocked model: it proves the component renders what the API returns, not a hardcoded value. **Playwright** runs the built app in a real browser against the real Go binary, so it proves the embedded build serves — not just the Vite dev server.

A minimal `App` renders the list, and a Vitest test stubs `fetch` with a fixture and asserts the DOM follows the model:

```tsx
// App.tsx
import { useEffect, useState } from "react";
import { fetchOrders, subscribeOrders } from "./api";
import type { Order } from "./types";

export default function App() {
  const [orders, setOrders] = useState<Order[] | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    const load = () =>
      fetchOrders(controller.signal)
        .then((next) => { setOrders(next); setError(null); })
        .catch((err: Error) => { if (err.name !== "AbortError") setError(err.message); });
    load();
    const unsubscribe = subscribeOrders(load);
    return () => { unsubscribe(); controller.abort(); };
  }, []);

  if (error) return <p className="err">Could not read /api/orders: {error}</p>;
  if (!orders) return <p className="subtitle">Loading…</p>;
  return (
    <ul>
      {orders.map((o) => (
        <li key={o.id} data-order-id={o.id}>{o.customer}: {o.total}</li>
      ))}
    </ul>
  );
}
```

```tsx
// App.test.tsx
import { render, screen } from "@testing-library/react";
import { afterEach, beforeEach, describe, expect, it, vi } from "vitest";
import App from "./App";

const orders = [
  { id: "o-1", customer: "Ada", total: 41, status: "paid", created: "2026-01-01T00:00:00Z" },
];

describe("App", () => {
  beforeEach(() => {
    vi.stubGlobal("fetch", vi.fn().mockResolvedValue({ ok: true, json: async () => orders }));
  });
  afterEach(() => vi.unstubAllGlobals());

  it("renders the orders the API returned, not hardcoded ones", async () => {
    render(<App />);
    expect(await screen.findByText("Ada: 41")).toBeInTheDocument();
  });

  it("shows an error instead of a blank page when the API fails", async () => {
    vi.stubGlobal("fetch", vi.fn().mockResolvedValue({ ok: false, status: 500 }));
    render(<App />);
    expect(await screen.findByText(/Could not read \/api\/orders/)).toBeInTheDocument();
  });
});
```

The Playwright config runs the real service on a dedicated port and never reuses an existing listener — reusing one makes the smoke test pass against the wrong server:

```ts
// playwright.config.ts
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  use: { baseURL: "http://127.0.0.1:19091" },
  webServer: {
    command: "cd .. && go run . -listen 127.0.0.1:19091",
    url: "http://127.0.0.1:19091/healthz",
    reuseExistingServer: false,
    timeout: 120_000,
  },
});
```

A Playwright smoke test asserts the page against the API payload and fails on any console error:

```ts
// e2e/orders.spec.ts
import { expect, test } from "@playwright/test";

test("the page renders the orders the API serves", async ({ page, request }) => {
  const orders = await (await request.get("/api/orders")).json();
  expect(orders.length).toBeGreaterThan(0); // a smoke test on an empty payload proves nothing
  const consoleErrors: string[] = [];
  page.on("console", (m) => {
    if (m.type() === "error") consoleErrors.push(m.text());
  });
  await page.goto("/");
  await expect(page.locator("[data-order-id]")).toHaveCount(orders.length);
  expect(consoleErrors).toEqual([]);
});
```

Every check needs a negative control: a test that would pass whether or not the feature works proves nothing. Assert the model's values (the counts, the text), and assert the error path (a `500` shows an error, not a blank page).

```makefile

FRONTEND_DIR ?= frontend

types:
	go run github.com/gzuidhof/tygo@$(TYGO_VERSION) generate

# on each caller so no path — build, test, e2e — can forget it.

frontend: types
	cd $(FRONTEND_DIR) && npm ci && npm run build

.PHONY: build
build: frontend
	mkdir -p bin   # -o bin/service fails on a fresh clone without this
	go build -o bin/service .

.PHONY: test-go
test-go:
	go test ./...

.PHONY: test-frontend
test-frontend: types
	cd $(FRONTEND_DIR) && npm ci && npm test

.PHONY: check-frontend
check-frontend:
	cd $(FRONTEND_DIR) && npm ci && npm audit --audit-level=high

.PHONY: lint vet vulncheck

	go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@$(GOLANGCI_LINT_VERSION) run ./...

.PHONY: vet

	go vet ./...

.PHONY: vulncheck
vulncheck:
	go run golang.org/x/vuln/cmd/govulncheck@$(GOVULNCHECK_VERSION) ./...

.PHONY: test check

```

`npm ci` (not `npm install`) keeps CI and local builds on the lockfile. On a fresh clone there is no lockfile yet, so run `npm install` once in `frontend/` to create `package-lock.json`, then **commit it** — every make target from then on uses `npm ci`. `npm run build` runs `tsc --noEmit && vite build`, so the type check and the bundle are one step, and `touch dist/.gitkeep` keeps the directory after `emptyOutDir`. The `npm audit --audit-level=high` gate fails the build on a high or critical advisory. `test` runs both suites — `test-go` for the Go packages and `test-frontend` for Vitest — because a service whose `make test` skips `go test ./...` is a service whose handlers are only tested by accident. The Go side's lint, vet and vulncheck are the three targets above, and `check` composes them with `check-frontend`. The fleet's fuller `check` — adding `osv-scanner` and `trivy` plus the shared ignore lists — is in `templates/Makefile.service` in this repository; copy those targets from there rather than retyping them, because `trivy` needs the ignore-file plumbing that is easy to get wrong by hand.

## Migration ownership

This guide records the stack. It does not decide which existing service adopts it. The per-app decisions — which service migrates now, which is rewritten next, which stays on its current stack — belong to the migration-ownership decision recorded in the adopting project's own planning as **Decide Which Go Service UIs Migrate to the React Stack**. That record is not part of this repository and nothing here depends on it: this guide stays stack-only, so the two cannot contradict each other.

## Changelog

### 2026-11-28 — attention-controller migration

Migrating a server-rendered Go page onto this stack (bborbe/attention-controller#356) surfaced these. Each is a rule for the next migration.

- **Mount the asset prefix, not just the root.** Mounting the page with `router.Path("/")` keeps the catch-all from shadowing the JSON routes, but the hashed Vite bundle under `/assets/` then never matches and the page renders an empty `#root`. Also mount `PathPrefix("/assets/")` — or register the catch-all last, as § The Go side: embed and serve does.
- **Put derived per-row view data in the API.** A server-rendered page computes values the item schema does not carry — jump target, navigation links, delivery timeline, risk. Return `Item + view` from the server's own row builder (e.g. `BoardItem { Item; Board BoardView }`, tygo `extends`) rather than re-deriving them in TypeScript; one builder keeps the two from drifting.
- **Keep a deploy gate's footer working with a marker element.** If a readiness probe reads a commit from the served HTML, have Vite emit a placeholder element — `<div id="build-identity"></div>`, since a comment may be stripped — and replace it per request in the page handler with the binary's build identity.
- **The existing e2e suite encodes the old DOM contract.** Expect three failures: selector gaps (emit the same `data-*` and class names), missing behaviour (port it), and specs asserting server-render internals — a row's DOM node swapped per SSE frame, HTML fragments in frames. Rewrite the last kind to wait on the client's re-fetch and assert the user-visible behaviour (form state carried across an update, later updates applied), with a negative control (§ Testing with Vitest and Playwright). When a new frontend spec disagrees with the old suite, the old suite is the contract.
- **Client-rendered pages race "read right after load" tests.** Start the first API fetch before React mounts, and turn a one-shot DOM read right after page load into a retrying wait with the same expected value.
- **Seed only after `/readiness`, not `/healthz`.** In a test harness `/healthz` can answer 200 while the store is still opening.
- **Record a baseline before demanding a green e2e.** The old suite failed 23 of 66 on master for a harness reason; a migration criterion compares branch failures against that recorded baseline ("no spec fails on the branch that passes on master"), never a bare exit 0.
- **SSE frames can shrink to `{type, id}`.** Once the client re-fetches on each event, the frame carries only the trigger. Diff on the serialised view entry server-side so an upsert fires only on a real change (§ Live updates with Server-Sent Events).
