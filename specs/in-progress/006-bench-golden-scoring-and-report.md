## Summary

- The bench runner produces a findings ledger and no score. `--golden` is declared and rejected with exit 2. This spec wires the scoring layer — the one layer of the runner that has never existed — and the per-run report page that makes a scored run readable without hand-reconstruction.
- Scoring is deterministic and offline: a pure function over ledger rows the runner already wrote and the golden set `bench/golden.json` already committed. No model is asked to judge anything, no review is invoked, no token is spent.
- The load-bearing decision: **a finding that matches no golden entry is not a precision failure.** The golden set was bootstrapped from one strong-model run, not hand-curated. A configuration that finds something the baseline missed is reported as a gap-triage candidate in its own section — evidence the golden set is incomplete, not evidence the configuration is wrong. Treating unmatched findings as precision failures would punish a better model for being better and freeze the baseline's blind spots as truth.
- Every scored run gets a page under `bench/reports/<config-hash>.md`, tracked in git — configuration identity, per-PR hit/miss table, gap-triage section, precision, recall, wall-time. The ledger is per-`(PR, config)` JSONL with no run marker; reconstructing "run 2 of 3" out of it was done by hand repeatedly and got wrong once.
- Runs are reconstructed by per-PR occurrence index, never by timestamp clustering. In the real ledger the gap between run 2's last row and run 3's first row is 48 seconds while gaps *inside* a run reach 140 seconds — no time threshold separates them, and the one that was applied by hand was the one that got it wrong.

## Problem

The benchmark exists to answer one question — did this rule change make reviews better or worse — and it currently stops one layer short of answering it. The runner resolves PRs, invokes the real review command, harvests findings, and appends a ledger row; then it stops. `bench/golden.json` has been written, validated against the baseline run, and carries 42 adjudicated entries with a settled match rule, and nothing reads it. The operator's only path from a ledger to a number is to open `bench/results/results.jsonl` by hand, chunk 66 rows across seven configurations into runs by eyeballing timestamps, match findings against golden entries mentally, and divide. That has been done repeatedly, it is slow, and it has already produced one wrong answer. Worse, the interesting signal — a configuration reporting something the baseline never found — has no place to be recorded at all, so it is either silently discarded or silently miscounted as a false positive. Until scoring exists, every rule change still ships blind, and the token cost already spent on 66 real review invocations produces no comparable number.

## Goal

One command turns a ledger and a golden set into a score and a durable report. Scoring is mechanical: the same ledger and the same golden set produce byte-identical output every time, with no model in the loop and no network access. The three golden states mean exactly what `bench/golden.json` says they mean — an unmatched `accepted` entry costs recall, a matched `rejected` entry costs precision, an `unreviewed` entry is excluded from both sides of both ratios. A finding matching no entry is surfaced as a gap-triage candidate under its own heading, never counted against precision, because the golden set is a bootstrap that sharpens through disagreement rather than frozen ground truth. Every configuration that has ever been run has a page in `bench/reports/` recording what it was, what it found, what it missed, what it found that the baseline did not, and how long it took — so that a PR changing a rule can carry the measured before/after as a committed diff instead of a claim.

## Non-goals

- Do NOT introduce an LLM judge, a fuzzy body matcher, an embedding comparison, or any non-deterministic matching. The match rule in `bench/golden.json` is settled and validated; fuzzy body matching was tried against the four-phrasing case and rejected. Scoring stays a pure function of text equality and substring containment.
- Do NOT re-derive, refine, or edit the match rule or the 42 signatures. Curating the golden set is data work, separate from the scorer; the scorer's job is to make disagreement visible so that curation has evidence to act on. `bench/golden.json` is a frozen input to this spec, byte-identical after it.
- Do NOT change `commands/pr-review.md` or anything under `rules/`. Either would move `rules_commands_hash`, which is the identity every existing ledger row was written under — every row in `bench/results/results.jsonl` and every published number in this spec would become unattributable in the same commit.
- Do NOT touch the harvester, `HarvestResult`, the `UNATTRIBUTABLE FINDING` gate, or the `NOT A REVIEW` gate. Finding extraction is spec 005's territory and is `verifying`; the scorer consumes what the harvester already wrote and re-harvests nothing.
- Do NOT fix D8 (extensionless paths such as `Dockerfile`, `Makefile`, `LICENSE` are unattributable because both harvest path gates require a dot). It is a known open defect in the harvest layer, out of scope here — but the scorer must not inherit the dot requirement, which is an acceptance criterion below.
- Do NOT add token counting or cost capture to the runner. The ledger carries no cost field today; the report states so rather than estimating. Capturing cost means parsing subprocess telemetry and is its own spec with its own baseline impact.
- Do NOT add automatic cache invalidation on a `bench/run.py` change. See Constraints — a scorer change does not require a cache clear at all, and auto-deleting a cache that cost real tokens on any edit to the runner is a worse failure than the one it prevents.
- Do NOT make the match rule, the three state names, the gap-triage classification, the run-chunking rule, the report location, or the ratio rounding configurable. All six are invariants; if a future consumer demands variation, that is a separate spec.
- Do NOT add an opt-out that counts unmatched findings as precision failures, or a flag that suppresses the gap-triage section. An escape hatch on this Goal is the regression this spec exists to prevent.
- Do NOT score, or publish a page for, a ledger row recorded against a PR manifest the golden set does not describe. Adjudicating a golden set for a probe manifest is separate work; scoring a `mode-full-probe` row against `golden-dev-1` produces a ratio over the wrong fixture and, once committed to `bench/reports/`, sits beside a valid page inviting a comparison that is invalid.
- Do NOT rewrite, migrate, deduplicate, or delete ledger rows. The ledger stays append-only and is read-only to the scorer.
- Do NOT commit `bench/results/` or `bench/.cache/`. They stay gitignored. Two frozen ledger *slices* under `bench/testdata/` and the report pages under `bench/reports/` are the two named exceptions, and the README states both.

## Acceptance Criteria

Each AC is tagged **[container]** (verifiable at prompt time with no network, no tokens and no real `claude` binary) or **[operator]** (only observable on the host, because it spends real tokens against the live review command). The convention is inherited from specs 002, 003, 004 and 005, whose operator criteria found every defect in the harvest family while the container suite found none.

**Why the fixtures are real ledger slices, not hand-written rows.** Five defects reached production in this codebase — D1, D2, D4, D7 and the whole of spec 005 — because the fixtures were written alongside the parser from the same mental template, so tests and code agreed with each other and both disagreed with the model's actual output. Every unit AC below binds to the **real committed `bench/golden.json`** and to **verbatim slices of the real ledger**, both pinned by published `sha256`. No AC below is satisfiable by a row a prompt authored.

## Desired Behavior

1. **`--golden` scores instead of refusing, and a second entry point scores what is already on disk.** `--golden <path>` supplied to a normal run scores that run's configuration after the last PR and rewrites that configuration's report page; because every completed `(PR, configuration)` pair is cache-served, repeating an already-run configuration with `--golden` invokes zero reviews and costs zero tokens. A score-only mode reads the ledger, scores **every** distinct `config_hash` in it, writes one page each, and invokes nothing — it is the path for configurations whose cache has since been deleted, which is the situation the ledger's historical rows are all in. Score-only requires `--golden` and rejects the identity flags, because a scored ledger's identity comes from its rows. `--reports-dir` defaults to `bench/reports`. Preconditions — a missing golden file, a golden set lacking `entries` / `match_rule` / `states`, an empty or absent ledger, a ledger line that is not valid JSON, a `config_hash` that is not 64 lowercase hex characters — each abort with exit 2 and a frozen literal on stderr, before any review subprocess starts.

   **The `prs_version` agreement is checked at the join where the comparison actually happens, which is per ledger row.** In a live run the golden set's `prs_version` is compared once against the manifest's `version` and a disagreement aborts with exit 2 before the first review, because the whole run would be measured against a fixture the golden set does not describe. In score-only mode there is no single manifest: each row carries its own `prs_version`, and the ledger routinely holds rows from throwaway probe runs against different manifests — 4 of the 66 rows on disk today, across 3 of the 7 configurations, carry `empty-diff-probe`, `mode-full-probe` and `ruleid-probe`. Those rows describe different diff ranges over a different PR set, so a recall computed for them against `golden-dev-1` is not a number, and committing such a page beside a valid one invites exactly the side-by-side comparison that is invalid. Every row whose `prs_version` differs from the golden set's is therefore **skipped before scoring**, named on stderr with the frozen literal `PRS VERSION SKIP` together with its `config_hash` and both versions; a configuration with no surviving rows gets **no page at all**, and a configuration with some surviving rows gets a page over the survivors whose Configuration block records how many of its rows were skipped. This is the same argument that freezes `rules_commands_hash`, applied to the other half of the configuration identity.

2. **Matching is deterministic and follows the settled rule exactly.** For each `(golden entry, finding)` pair within the same `pr_id`: if both sides carry a non-null `rule_id`, they match when those ids are equal and do not match otherwise — a rule-id disagreement is decisive and no fallback is attempted. Otherwise they match when `path` is string-equal and **every** keyword in the entry's `signature` appears as a case-insensitive substring of the finding's `body`. Otherwise they do not match. `line` is read from neither side; it is display data on the report and identity nowhere. Path comparison is whole-string equality with no extension requirement, so an extensionless path compares like any other. No fuzzy comparison, no token overlap, no similarity threshold, no model. Matching is a relation, not an assignment: an entry is hit when at least one finding matches it, and a finding is unmatched when it matches no entry, so a single finding covering two entries hits both and neither side needs a pairing algorithm.

3. **The three golden states mean what the golden set says, and unmatched findings mean something else entirely.** An `accepted` entry with no matching finding is a recall miss. A `rejected` entry with a matching finding is a precision penalty. An `unreviewed` entry is excluded from both numerator and denominator on both ratios, and a finding matching one is neither a penalty nor a candidate — it is simply not adjudicated. A finding matching **no** entry is a **gap-triage candidate**: reported under its own heading, quoted verbatim with its PR, path and line, and counted against nothing. This is the spec's load-bearing decision and it is not a matter of taste. The golden set is bootstrapped from a single strong-model run, not hand-curated ground truth — its own `scoring_note` says so. When several independent configurations agree on a finding the baseline missed, that is evidence the golden set is **incomplete** and the entry is a candidate for promotion to `accepted`; when nothing ever reproduces a baseline finding, it is a candidate for demotion to `rejected`. Counting unmatched findings as precision failures would punish a better model for being better and would freeze the baseline's blind spots as truth. This is not hypothetical: `bench/golden.json`'s `known_corrections` records that `tts-mcp#20` was annotated "clean — correct answer is zero findings" on the strength of six consecutive zero-finding runs from a weaker model, and the strong model then found a real, hand-verified defect in it. The gap-triage section is where that correction would have surfaced automatically.

4. **Ratios are defined on every input, including the degenerate ones.** Recall is accepted hits over accepted entries in scope; precision is accepted hits over accepted hits plus matched `rejected` entries. Both render as three fixed decimals. When a denominator is zero — no `accepted` entries in scope, or no matched entries at all — the ratio renders as the literal `n/a` and the run reports its raw counts alongside. Nothing divides by zero, nothing renders a zero denominator as `0.000`, and an all-`unreviewed` golden set produces a complete report with both ratios `n/a`. Two honest consequences are stated on every page, in the page's own words, because a headline ratio read without them is worse than no ratio. First, with zero `rejected` entries in `golden-dev-1`, precision cannot currently be lost by any configuration, so a precision of `1.000` is a property of the golden set's adjudication state and not yet a result. Second, **36 of the 42 signatures embed a line reference, so a re-report of the same issue at a different line does not match and is surfaced as a gap-triage candidate rather than a hit** — on this golden set `recall` measures whether a configuration cited the same line, not whether it found the issue. The recall caveat is the larger distortion of the two and is measured, not assumed: across the four runs of `9ce66e05…` only 5 of 16 findings hit an entry, 3 of those through the 6 signatures that carry no line reference and 2 through a finding that happened to cite the same line — zero hits came from a line-shaped signature matching a differently-lined re-report. Both sentences live on the page and in `bench/README.md`, not only in this spec, because a caveat that dies with the spec is the doc-disagrees-with-repo failure that produced D1, D2, D4, D7 and spec 005.

5. **A run is a per-PR occurrence index, never a timestamp cluster.** Within one `config_hash`, the k-th ledger row for a given `pr_id`, in ledger file order, belongs to run k. Run boundaries therefore need no clock, no threshold and no tuning, and survive clock skew, a slow PR, and an operator pausing between PRs. A run that does not cover every PR in the manifest is labelled partial on the page, because a PR that failed loudly leaves no row and its absence must be visible rather than shifting every later row into the wrong run. A partial run is scored over the PRs it actually covers: the golden entries of the PRs it does not cover are **out of scope for that run, not misses**, so a run covering three of the five fixture PRs is scored against 24 entries and a run covering one is scored against 1. Charging a partial run the full 42 would report a recall collapse where the only event was a PR that never ran. This is not a hypothetical branch — config `dc7efd9d…` chunks into eight runs with the coverage vector `[5, 5, 5, 5, 5, 3, 3, 1]`, and AC30 pins all eight. The alternative — clustering by a gap in `started_at` — is not merely inelegant, it is wrong on the data that exists: the boundary between run 2 and run 3 of config `9ce66e05…` is 48 seconds while gaps *within* runs 1, 2 and 4 reach 140, 128 and 110 seconds, so no threshold separates runs without also splitting one, and the threshold applied by hand is the one that produced the wrong answer.

6. **Every scored configuration has a committed page that answers "what was this and what did it find".** `bench/reports/<config_hash>.md` — the full 64-character hash, because a truncated filename reintroduces the identity ambiguity the hash exists to remove — is tracked in git, unlike `bench/results/` and `bench/.cache/`, so a PR that changes a rule carries its measured before/after as a reviewable diff. The page carries: a **Configuration** block (model, effort, mode, `config_hash`, `rules_commands_hash`, `prs_version`, the `coding` plugin version read from `.claude-plugin/plugin.json` at scoring time with the measured identity named as `rules_commands_hash`, the golden set's `version`, `prs_version` and `baseline.coding_version`, every distinct `runner_version` present in the scored rows, the count of that configuration's rows skipped for a `prs_version` disagreement, the two mandated ratio caveats of DB4 in the page's own words, and a line stating that cost is not recorded because the ledger carries no cost field); a **Runs** table (one row per run with span, PR coverage, complete/partial, golden entries in scope, findings, hits, misses, matched `rejected`, gap candidates, recall, precision, total wall-time — the in-scope column is what makes a partial run's smaller denominator visible instead of implied); a **Per-PR** table (per run and PR: golden entries in scope, hits, misses, findings, gap candidates, `duration_seconds`); and a **Gap-triage candidates** section quoting each unmatched finding with its PR, path and line under a sentence stating in those words that these are **not a precision failure**. The page is a total function of the ledger and the golden set: it is rewritten wholesale on every scoring, never appended to, and contains no generation timestamp — so re-scoring an unchanged ledger produces a byte-identical file and a noisy diff always means the data changed.

7. **The scorer reads and never writes anything but report pages.** It re-harvests nothing, reopens no raw capture, mutates no ledger row, edits no golden entry, and runs no `git` command. Because it consumes findings the harvester already normalised, a change to the scorer never invalidates a cached review — cached rows stay exactly as valid as they were, and the cache-clearing rule stated in `bench/README.md` continues to apply to harvester changes alone, where the config hash's blindness to `bench/run.py` genuinely matters. Cache invalidation stays manual and stays the operator's call; the report surfaces every distinct `runner_version` among the rows it scored so that a ledger mixing pre- and post-005 harvest output is visible on the page rather than silently averaged.

## Constraints

- **Language and dependencies:** Python 3 standard library only. Changes land in `bench/run.py`, `bench/test_*.py`, `bench/testsupport.py`, `bench/testdata/`, `bench/README.md`, `bench/reports/` and `CHANGELOG.md`. No packaging, no third-party imports, no new top-level files outside `bench/`.
- **`bench/golden.json` is a frozen input.** Byte-identical after this work — `git diff --exit-code bench/golden.json` exits 0. Its `match_rule`, its three `states` definitions, its 42 entries and their 36 `path:line`-shaped signatures are data, not code, and are not edited here.
- **The measured configuration is untouched.** No rule, agent, command or doc that participates in a review is edited, including `commands/pr-review.md`. `bench/prs.json` stays frozen at `dev-1`. Either would move `rules_commands_hash` and orphan every existing row and every number published in this spec.
- **The harvest layer is untouched.** `harvest`, `HarvestResult`, the attribution extractor, the `UNATTRIBUTABLE FINDING` gate and the `NOT A REVIEW` gate keep their current behaviour and their current tests. D8 (extensionless paths unattributable, both harvest path gates requiring a dot) is a known open defect that stays open; the scorer must not replicate its dot requirement (AC20).
- **The 103 existing tests keep passing and their assertions are not weakened.** No test function may be deleted and no assertion relaxed; the suite's count after this work is strictly greater than 103. Evidence is AC24's per-file assertion floors, because a surviving `def test_` with an emptied body satisfies both a deleted-test check and a test-count check.
- **The six existing `bench/testdata/` fixtures are frozen.** `sample-report.md`, `real-capture-report.md` and the four `capture-*.md` captures are byte-identical after this work and still harvest to their asserted results.
- **The ledger is append-only and read-only to the scorer.** No row is rewritten, deduplicated, reordered or deleted; `bench/results/` and `bench/.cache/` stay gitignored; the scorer opens the ledger for reading only.
- **Committed-output exceptions are exactly two, and the README states both.** `bench/README.md`'s "no benchmark output is ever committed" invariant is amended in this work to name the report pages under `bench/reports/` and the four frozen ledger slices under `bench/testdata/`. Nothing else from a run is committed. Leaving the invariant unamended while committing both would put the doc and the repo in the disagreement that produced D1, D2, D4, D7 and spec 005.
- **A scorer change requires no cache clear, and cache invalidation is never automatic.** The config hash covers `rules/` + `commands/` but not `bench/run.py`, so a change to the runner does not move it and cached rows are silently reused. That matters for harvest changes — where `bench/README.md` already instructs the operator to delete `bench/.cache/reviews/` and `bench/results/` and re-run — and does not matter for scoring, which consumes already-normalised findings and can be re-run offline over the existing ledger for free. Automating the deletion is rejected outright: it would destroy a cache that cost real tokens on any edit to an unrelated function in the same file.
- **Frozen invariants** (not configurable, not flagged): the match rule and its priority order; the exclusion of `line` from identity; the three state names and their semantics; the gap-triage classification; the run-chunking rule; the report location and filename form; the three-decimal ratio rendering and the `n/a` literal; the absence of a generation timestamp; the precondition marker literals `GOLDEN SET NOT FOUND`, `INVALID GOLDEN SET`, `GOLDEN VERSION MISMATCH`, `PRS VERSION SKIP`, `EMPTY LEDGER`, `CORRUPT LEDGER`, `INVALID CONFIG HASH`; and everything spec 002–005 already froze (45-minute review timeout, cache/results/failure-artifact locations, isolated config directory, required section names).
- **Values read from the ledger are data, never paths.** A `path`, `rule_id` or `body` read from a finding is rendered into a report page and used for nothing else — never opened, stat-ed, joined onto a filesystem root, or passed to a subprocess. The only ledger value that reaches a filename is `config_hash`, gated by a 64-lowercase-hex check.
- **Repo conventions that must not regress** (`docs/dod.md`): no personal paths (`/Users/`, `~/Documents/`) in any shipped file including the four ledger slices; a `## Unreleased` CHANGELOG entry using conventional prefixes per `docs/changelog-guide.md`, describing the whole change rather than the last prompt's slice.

## Assumptions

- **The golden set and the four ledger slices are installed by the operator before approval, not by any prompt.** `bench/golden.json` is currently untracked and `.gitignore:8` excludes `/bench/results/`, so a container clone reaches neither. The operator commits all five files before `dark-factory spec approve`; every prompt therefore finds them present and writes only code and tests against them. All four slices were checked for personal paths and contain none. A prompt that finds a file missing or digest-mismatched stops and reports it; handing an agent a fully published acceptance shape and an unreachable source is what makes synthesis the default path, so the source is made reachable instead.
- **Every published number in this spec was computed against the real files, not estimated.** The baseline self-match (42/42/0/0), the four-run table, the per-PR breakdown, the flipped-state results (41/1 rejected, 41/0 unreviewed, 0/0 all-unreviewed), the eight-run partial table with its `[5, 5, 5, 5, 5, 3, 3, 1]` coverage vector and 24/24/1 out-of-scope arithmetic, the 4-probe-row skip arithmetic, and the 48s-vs-140s timestamp evidence were each measured on 2026-08-09 against `bench/golden.json` at digest `90f5b0a6…` and `bench/results/results.jsonl` as it then stood. A prompt that reproduces the match rule faithfully reproduces these numbers; a prompt that cannot has changed the rule.
- **36 of the 42 signatures are `path:line`-shaped single keywords and 4 entries carry a `rule_id`.** The signatures were derived mechanically from the baseline run and verified to partition its 42 findings with zero overlaps and zero unmatched — against that run. Consequently the signature is line-coupled in practice for most entries, and a differently-phrased report of the same issue at a different line does not match: the `apt-key` issue in `.github/workflows/ci.yml` appears in all four sonnet runs at lines 13, 29, 9 and 27 and is a gap-triage candidate every time. That is a property of the golden set's current curation state, not of the scorer, and refining it is data work outside this spec. Surfacing it is exactly what the gap-triage section is for, and the numbers in AC5, AC13 and AC30 encode this behaviour deliberately. The caveat itself does not live here: DB4 mandates it on every report page and AC22 requires it in `bench/README.md`, because this Assumptions section disappears when the spec completes while `bench/reports/9ce66e05….md` stays in the repo with a headline `recall 0.048` on it forever.
- **The five fixture PRs stay merged, their recorded SHAs stay reachable, and `dev-1` stays the manifest version.**
- A stub executable on `PATH` printing a chosen payload and exit code is sufficient to prove the scorer invokes no review; `bench/testsupport.py` already provides it.

## Security / Abuse Cases

- **Attacker-controlled surface:** ledger `body`, `path` and `rule_id` values originate in review subprocess output, which is influenced by the content of the reviewed repository. The scorer reads more of that text than any previous layer and renders it into a file.
- **Rendered values are data, not paths.** No `path`, `rule_id` or `body` from a finding is opened, stat-ed, joined onto a filesystem root, globbed, or passed to a subprocess. A finding citing `../../etc/passwd:1` produces a table cell containing that string and no filesystem access.
- **The one ledger value that becomes a filename is gated.** `config_hash` is used to name the report page and is rejected unless it matches 64 lowercase hex characters, so no ledger row can direct a write outside the reports directory (AC21).
- **No evaluation, no execution:** the scorer matches strings, counts, formats and writes. No value reaches a shell; the runner continues to invoke subprocesses with argument lists rather than shell strings.
- **Markdown injection into the page is contained:** a finding body containing table pipes, headings or fences can make a page render oddly. It cannot escape the file, and the page is a derived artifact regenerated on every scoring — the mitigation is that the page is never a trusted input to anything, and no tool parses it back.
- **Denial by volume:** a run can carry thousands of findings. Matching is linear in `entries × findings` within a PR and rendering is linear in output size; there is no construct in a ledger row that causes unbounded backtracking.
- **Secret leakage:** the page reproduces ledger content and the plugin version, and nothing else — no environment variables, no tokens, no credential material. The four committed ledger slices were checked for personal paths before installation.
- **Fail-closed on identity, fail-open on curation.** Every ambiguity about *which configuration* a page describes resolves to rejection (exit 2, frozen marker). Every ambiguity about *whether a finding is correct* resolves to reporting it as a gap-triage candidate rather than scoring it, because a wrong score is cited and a triage candidate is read.

## Do-Nothing Option

Doing nothing leaves the benchmark one layer short of its purpose: 66 real review invocations have already been paid for and produce no comparable number, and the only path from ledger to score is manual, slow, and has already been wrong once. The alternatives considered: (a) keep scoring by hand — the run-chunking evidence alone disqualifies it, since the boundary the operator has to spot is 48 seconds wide while gaps inside a run reach 140 seconds, and the error is silent because a hand-chunked run still produces a plausible ratio; (b) score with an LLM judge instead of a match rule — non-deterministic by construction, so re-scoring the same ledger would produce different numbers and the report could never be a committed diff, which is the artifact that makes a rule change reviewable; (c) score but count unmatched findings as precision failures — cheaper to implement and actively harmful, since it would have scored the strong model's real, hand-verified `tts-mcp#20` defect as a false positive and confirmed the annotation that the golden set's own `known_corrections` records as false; (d) curate the golden set further before building the scorer — inverted, because curation needs the disagreement evidence that only the gap-triage section produces, and the set's line-coupled signatures will not improve until something mechanically surfaces the four-phrasing cases; (e) ship the score without the report page — leaves the number without the configuration identity, the per-PR breakdown or the gap candidates, which is the shape that already got a hand-reconstructed run wrong. Every input exists on disk today, the match rule is settled and validated, and the layer below it is complete.
