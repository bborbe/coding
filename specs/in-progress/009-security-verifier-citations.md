## Problem

Tasks 1–2 shipped the mechanical rule base and the evidence-pointered security-model derivation, and the selector-mode guide already documents that invariant-kind findings cite `invariant_id` — with validation deferred to this task. Today a finding can cite an invented `invariant_id` and pass the funnel unvalidated, dependency (toolchain) findings have no formal `kind` entry in the polymorphic contract, and high-severity security findings emit with no falsification check — so the admin-override treadmill the design set out to fix (verdict coupled to severity) is still unaddressed. Security Review Mode needs the precision half of the judge→recall / verifier→precision split before it can ship a gate that blocks merges on real findings only.

## Goal

After this work, every security finding that flows through the review funnel carries exactly one provenance kind — `rule` (resolves in `rules/index.json`), `invariant` (resolves in the derived `security-model.json`), or `toolchain` (tool-output, no id) — and `scripts/validate-citations.sh` enforces that contract fail-closed: an invariant finding without a resolvable model is dropped, never kept. High-severity findings cannot emit without passing the `security-verifier` falsification gate, and every survivor carries `counterevidence_checked`. Blocking is derived orthogonal to severity (`confirmed ∧ high exploitability ∧ impact ≥ medium`), documented with a per-surface thresholds table (local / bot / audit) and defaults that ship untuned. All of this is documented in the dormant Security Extension — the contract exists now and is active the moment a command sets the security-review signal (task 4).

## Security / Abuse Cases

The validator reads untrusted JSON (LLM-adjudicated findings) plus `rules/index.json` and an operator-chosen model file; it parses JSON, matches ids, and writes nothing.

- **Attacker-controlled input:** the findings JSON is LLM output — untrusted content. It is JSON-parsed and id-matched only, never executed, never echoed into a shell. The existing contract already gates hallucinated `rule_id`s; this extension extends the same gate to `invariant_id` (a hallucinated invariant now drops fail-closed instead of passing unvalidated).
- **Trust boundary:** `SECURITY_MODEL_FILE` is operator-controlled (env var), same trust class as `INDEX_FILE`. A malicious value points the script at an arbitrary JSON file; the script only `json.load`s it and matches `invariants[].id` — no execution, no writes, no path traversal reachable surface. A malicious model cannot inject behavior; worst case it wrongly accepts or rejects an `invariant_id` within the file the operator chose.
- **Fail-closed bias:** absent model → findings dropped, never kept. The failure mode is a false drop (drift signal), not a false keep.
- **Provenance spoofing:** a finding could declare `kind: toolchain` to skip citation. This is the existing tool-output contract (toolchain findings carry no rule_id by design, per `go-security-specialist.md`); the verifier gate is the precision control that applies to high-severity findings regardless of kind. The spec does not weaken the gate.
- **Exactly-one-provenance:** a finding carrying both `rule_id` and `invariant_id` is validated only against the field named by `kind`, preventing double-attribution or ambiguity.
- **Hang/retry:** the validator is a bounded single-pass script over already-present files; no retry loop, no network, no unbounded scan.
- **CLAUDE.md Doc↔Agent table:** no row added in this task (recorded decision); the verifier's contract is its own agent file, and the README row lives in the "Other agents" grouping, not in any dispatch list.
